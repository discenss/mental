# materials/ — исходные материалы по темам

Сюда компаньон, который ведёт контент, кладёт всё сырьё по каждой программе:
методические тексты, сценарии медитаций/аудио-практик, черновики — в любом
формате (`.md`, `.doc`/`.docx`, обычный текст).

Это не документация разработки (она в [../docs/](../docs/)) и не готовый
контент, с которым уже работает бэкенд (он в [../content/](../content/)).

## Структура — по программе, не по типу файла

```
materials/
├── programs/
│   ├── bound/        Личные границы           (программа уже есть)
│   ├── real/          Найти себя и вернуть смысл (программа уже есть)
│   ├── anx/           Тревога и внутреннее напряжение
│   ├── emo/           Эмоциональная регуляция
│   ├── past/          Прошлый опыт и его влияние на настоящее
│   ├── burn/          Выгорание и восстановление энергии
│   ├── focus/         Фокус и выход из прокрастинации
│   ├── self/          Самооценка и внутренний критик
│   ├── rel/           Отношения и повторяющиеся сценарии
│   ├── proc/          Автоматические реакции и паттерны
│   └── sport/         Вертикаль для спортсменов
└── shared/            Стандарт, маркетинг, юр. тексты — не привязано к одной теме
```

Внутри папки программы — **всё вместе**: методический текст недели, сценарий
медитации, черновик квиза. Не нужно решать, в какую из четырёх папок класть
файл — только в какую программу. Один файл — один кусок смысла (одна неделя,
одна практика), не «всё про BOUND одним файлом на 200 КБ».

## Присылаете материал впервые?

Инструкция без технических подробностей — [CONTRIBUTING.md](CONTRIBUTING.md):
как добавить файл через сайт GitHub, как называть, какой формат, что запрещено.

## Откуда и куда течёт материал

```
materials/programs/<код>/   ← сюда кладут сырьё
   ↓  перевод в структуру
content/modules/<код>.yaml  ← эталонный контент, грузится в БД
   ↓  загрузка
backend (Postgres)          ← то, что видит пользователь
```

Правка в `materials/` **не меняет продукт сама по себе** — её переносят
в `content/` и перезагружают. Материал здесь может опережать то, что в проде —
это нормально, так и задумано.

## Правила

1. **Формат — любой, в котором автору удобно писать**: `.md`, `.doc`/`.docx`,
   обычный текст. Для Word-файлов разработчик сам сделает `.md`-версию для
   истории правок — автору об этом думать не нужно.
2. **Персональные данные сюда не попадают.** Ни примеров из реальных дневников
   пользователей, ни их скриншотов. Нужен пример — придумайте его.
3. **Большие бинарники (готовые mp3) — не сюда.** Текст сценария — да, готовую
   запись — в `content/audio/` (вне git, см. [../.gitignore](../.gitignore)).

## Терминология — обязательна к соблюдению

Нормативные запреты (§16 стандарта), действуют и в материалах, и в коде:

- **«диагностика» — запрещено** в любых пользовательских текстах.
  Пишем **«самопроверка»**.
- Не «модуль», а **«маршрут»** или **«программа»**.
- Формулировка «мы не ставим диагнозов и не заменяем работу с психологом»
  обязательна там, где описывается суть продукта.

Тон: спокойный, без давления, на «вы». Ориентир — [../bot/texts.py](../bot/texts.py).
