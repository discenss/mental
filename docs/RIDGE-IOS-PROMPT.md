## 0. Что за продукт Ridge

Психологическая поддержка через **линейные 6-недельные программы**. Программа = 6 недель × 7 дней,
единый ежедневный поток. Реализованы 2 программы из 10 направлений: **BOUND** («Личные границы»)
и **REAL** («Найти себя и вернуть смысл»). Остальные 8 в планах, плюс партнёр планирует
вертикаль для спортсменов.

Маршрут **линейный и одинаковый для всех** — ветвится только показываемый текст, не
последовательность дней. Выбор зоны и маршрута **детерминированный** (правила + заготовленные
тексты), НЕ ИИ. ИИ используется только в трёх местах: «Спросить ИИ», разбор недели, итог программы.

Прочитай перед началом:
- `~/dev/mental/docs/mental-architecture.md` — канонический Flow (день/неделя/программа), 4 слоя
  «диагностики», модель данных, §-нормативы. **Главный документ по смыслу продукта.**
- `~/dev/mental/docs/RUNBOOK.md` — запуск, env, все принятые решения и фиксы.
- `~/dev/mental/docs/NAMING-CONTEXT.md` — почему продукт называется Ridge (бывший «Mental Club»).

## 1. Задача

Создать `~/dev/mental/ios/Ridge/` — SwiftUI-приложение под iOS 17+, работающее против
Mental-бэкенда, консистентное с существующим Telegram-ботом (`~/dev/mental/bot/`) по логике
и формулировкам, и визуально наследующее дизайн-систему Rhythmos.

**Язык на этом этапе — только русский.** Английский добавим позже, но с первого дня:
- все пользовательские строки идут через `Localizable.xcstrings`, НЕ хардкодятся в вью;
- форматтеры дат берут локаль из выбранного языка, а не `Locale(identifier: "ru_RU")`;
- экран выбора языка есть, активен только русский, остальные (English, Español, Deutsch,
  Português) показаны неактивными/«скоро».

Это прямое требование: в Rhythmos локализацию не сделали (в `Localizable.xcstrings` всего
5 строк, всё остальное — русский хардкод, форматтеры прибиты к `ru_RU`), и это оказалось
дорого исправлять потом. В Ridge так делать нельзя.

## 2. Что берём из Rhythmos — и чего НЕ берём

### Берём почти без изменений

**Скелет проекта** (`~/dev/rhytmos/ios/RhytmosLive/`):
- Структура `Sources/{App,Models,Services,ViewModels,Views,DesignSystem}`.
- `Config/*.xcconfig` — **обязательно скопировать этот подход.** Team ID и bundle id вынесены
  из UI Xcode в файлы: `Shared.xcconfig` (общие настройки), `Debug/Beta/Release.xcconfig`
  (bundle id + PRODUCT_NAME на конфигурацию), `Local.xcconfig` (Team ID, в `.gitignore`) +
  `Local.xcconfig.example`. Свой платный Apple Developer аккаунт у владельца **есть**, так что
  в `Release.xcconfig` ставится реальный Team ID (в Rhythmos там плейсхолдер — это его история,
  не наша). Bundle id: `day.ridge.app`, `.dev`, `.beta` (домен продукта — `ridge.day`).
  Образец и объяснение решений — `/srv/rhythmos/MIGRATION.md` на сервере 108.181.215.222
  (в локальной копии Rhythmos каталога `Config/` НЕТ, он только на сервере — читай оттуда).
- Точка входа: `@main struct RidgeApp: App` с `@UIApplicationDelegateAdaptor` и одним
  app-wide `@StateObject AuthViewModel`; остальные VM создаются локально по вью.
- Роутинг через `RootView` + `enum AuthState: Equatable { loading, needsWelcome, unauthenticated,
  needsOnboarding, ready }` без associated values (это нужно для `.animation(_:value:)`),
  `switch` в `Group`, `.task { await auth.restoreSession() }`.
- HTTP-слой `RhytmosAPI`: пять приватных generic-глаголов (`get`/`getOptional`/`post`/`patch`/
  `delete`) + `makeRequest` + `execute` + `apiError`, обрабатывающий три формы FastAPI-детали
  (строка, вложенный объект с `message`, отсутствие). ~85 строк — это ядро, копируй.
- Паттерн ViewModel: `@MainActor final class XViewModel: ObservableObject` с `@Published`,
  канонический метод «set loading → clear error → do/catch → clear loading».
- Соглашения Codable: явный `enum CodingKeys: String, CodingKey` в каждой структуре
  (НЕ `keyDecodingStrategy = .convertFromSnakeCase`), ключи без переименования — одной строкой.
- `MainTabView`: `TabView(selection:)`, каждая вкладка в своём `NavigationStack`, file-scope
  `enum MainTab`, `.tint(t.terracotta)`, и приём с прокинутым замыканием для перехода между
  вкладками (`HistoryView { selectedTab = .today }`).

**Дизайн-система целиком** (`Sources/DesignSystem/`, 7 файлов) — точные значения:

Палитра (sRGB, alpha 1.0): Paper `#FAF6F0` · Surface `#FFFFFF` · SurfaceSecondary `#F5F1EB` ·

### НЕ берём — и это важно

Исследование Rhythmos нашло дефекты, которые **не нужно тащить в Ridge**:

1. **`Package.swift` — мусор, удалить.** Он объявляет executable-таргет с именем `Bios`
   (осталось от старого кодового имени) и не может собрать SwiftUI .app вообще. README
   Rhythmos врёт, предлагая открывать его. Настоящая точка входа — `.xcodeproj`.
2. **Нет dark mode.** Все 25 colorset'ов имеют один universal-вариант без `appearances`.
   В Ridge **сразу задай light+dark для каждого цвета** — переделывать потом дороже.
3. **JWT в `UserDefaults`, а не в Keychain** (плюс там же user id). В Ridge — **Keychain**.
4. **Нет обработки 401 и истечения сессии.** Нет интерсептора; 401 превращается в общую
   ошибку, а `restoreAuthenticatedState()` не отличает сбой сети от сбоя авторизации —
   любая ошибка `GET /me` роняет в `.unauthenticated`. В Ridge: отдельная ветка для 401
   (разлогин) против сетевой ошибки (показать «нет связи», сохранить сессию).
5. **`@Environment(\.theme)` объявлен, но не используется** — каждый компонент берёт
   `Theme.warm` напрямую. Либо используй environment честно, либо не объявляй.
6. **Мёртвые токены:** `Done`/`Partial`/`Skipped` побайтово дублируют `Sage`/`Amber`/`InkDim`
   и не используются; четыре `*Label`-цвета не используются и противоречат хардкоду в карточках.
   Не копируй мёртвый слой — заведи статусные цвета один раз и используй.
7. **Нет тестов, нет `#Preview`, нет accessibility-подписей** на кастомных контролах.
   В Ridge добавляй `#Preview` к каждому экрану и accessibility-labels к кастомным контролам.
8. **Синглтон API захардкожен в каждой VM** (`private let api = RhytmosAPI.shared`), без
   протокола — VM нетестируемы. В Ridge: протокол + инъекция, чтобы можно было подставить мок.
9. **Нет отмены запросов, таймаутов, ретраев** (`URLSession.shared` с дефолтами).
   В Ridge: своя `URLSessionConfiguration` с таймаутами, хранение `Task` для отмены.
10. **Экран `PracticesLibraryView` (234 строки) недостижим** ни из одной вкладки — мёртвый код.
    Не оставляй недостижимых экранов.

## 3. Архитектура: три решения, уже принятые владельцем

### 3.1. Аутентификация — Apple Sign-In + Google Sign-In + link-коды

**Текущее состояние бэкенда: аутентификации НЕТ вообще.** Это подтверждено исчерпывающе:
единственный `Depends()` во всём `main.py` — это `Depends(get_db)`. Нет `HTTPBearer`,
нет JWT, нет API-ключей, нет CORS. Пользователь опознаётся телом запроса:
`{provider, provider_user_id}` (провайдер из `{"telegram","ios","whatsapp"}`) либо голым
`{user_id}` целым числом.

Из этого следуют дыры, которые надо закрыть, потому что публичное приложение их обнажает:
- `{"user_id": N}` перебором даёт доступ к любому аккаунту;
- `eid` в 14 эндпоинтах — голое угадываемое число **без проверки владельца**
  (`_enrollment` делает `db.get(Enrollment, eid)` и не сверяет `user_id`);
- `POST /api/v1/users/reset` уничтожает весь прогресс, без подтверждения и без авторизации;
- `POST /api/v1/reminders/due` без авторизации выгружает `provider_user_id` всех
  пользователей вместе с их программой и позицией в ней.

**Что делать:** реализовать в `~/dev/mental/backend` слой авторизации и провести iOS через него:
- **Apple Sign-In** — верификация identity token на бэкенде, `provider="ios"`
  (это значение уже есть в `identity.PROVIDERS`), `provider_user_id` = Apple user identifier.
  Apple требует Sign in with Apple в App Store, если есть другие способы входа — так что он
  обязателен в любом случае.
- **Google Sign-In** — верификация id_token на бэкенде. Понадобится новое значение провайдера
  (например `"google"`) — добавь в `identity.PROVIDERS`.
- **Свой токен сессии** (JWT), выдаваемый бэкендом после верификации у провайдера, и
  **проверка владельца** на всех enrollment-эндпоинтах. Токен — в Keychain.
- **Link-коды для Telegram и WhatsApp** — чтобы один человек в боте и в приложении был одним
  пользователем, а не двумя. Механизм уже работает в Rhythmos: бот выдаёт 6-значный код,
  приложение его принимает, аккаунты сливаются. Образец —
  `~/dev/rhytmos/backend/app/routers/auth.py` (`/api/v1/auth/link-account`) и
  `SettingsView` в iOS Rhythmos. `identity.PROVIDERS` в Mental уже содержит `"whatsapp"`.

Сначала сделай бэкенд-часть, потом iOS: писать клиент против несуществующей авторизации
и переделывать потом — хуже.

### 3.2. Поток шагов дня — вынести в бэкенд, один источник истины

`GET /api/v1/enrollments/{eid}/today` отдаёт **сырой день**, а не последовательность шагов:
`{status, done_today, session, week, day, day_title, week_intro{...}, focus, task{text,subtasks},
quiz{kind,question,options,correct,saves_free_text}, reflection[3], intent_questions, audio{code,title}}`.

Сама последовательность прохождения (`day_steps`) — **конструкция только Telegram-бота**:
grep по репозиторию находит `day_steps` исключительно в `bot/handlers/flow.py` и в RUNBOOK.
Это значение FSM, а не поле JSON. Строится двумя функциями в боте:
- `_build_morning_steps(today)`: по одному `{kind:"info"}` на каждый `intent_questions`
  → один совмещённый `{kind:"info"}` с фокусом + заданием + подзадачами → если есть
  `audio`, то `{kind:"audio", code, title}`;
- `_build_evening_steps(today)`: `{kind:"focustask"}` → если есть квиз, `{kind:"quiz",
  question, options}` → по одному `{kind:"free_text", prompt}` на каждый из 3 вопросов рефлексии.

**Решение владельца: вынести сборку шагов в бэкенд** и отдавать готовые `day_steps` новым
эндпоинтом. Тогда Telegram и iOS рендерят одно и то же, и логика прохождения дня не разъедется
между двумя реализациями. Бот после этого переводится на тот же эндпоинт.

Это надо сделать **до** написания iOS-экрана дня.

### 3.3. Иконки — SF Symbols

Иконки к вопросам рисуются **SF Symbols**, как уже сделано в онбординге Rhythmos
(там у каждого варианта ответа символ: `"flame"`, `"wind"`, `"battery.25"`, `"cloud.fog"`,
`"lock.shield"`, `"moon.zzz"`, `"questionmark.circle"`). Никаких растровых ассетов:
SF Symbols бесплатны по весу, сами подстраиваются под размер шрифта, тему и dark mode.

Подобрать символы: каждому из **10 направлений интейка** (ANX тревога, EMO эмоции,
PAST прошлый опыт, BURN выгорание, FOCUS фокус/прокрастинация, SELF самооценка,
REL отношения, BOUND границы, PROC паттерны, REAL поиск себя) и каждому типу шага дня
(фокус, задание, аудио, квиз, рефлексия, маркеры, самопроверка).

В `~/dev/rhytmos/rhythmos-icons/` лежит **иконка приложения** (AppIcon в размерах), а не
иконки к вопросам — не путай, для Ridge нужна своя иконка приложения.

## 4. Экраны Ridge

Владелец задал структуру: **основной экран как в Rhythmos** (задание на день), **История —
вторая вкладка**, **третья вкладка — «Пройденный путь»** с недельной и итоговой аналитикой.
Четвёртая вкладка — настройки («Я»), как в Rhythmos.

### Вкладка 1 — «Сегодня» (день программы)

Композиция берётся с `TodayView` Rhythmos (518 строк): `ZStack` над `t.paper`, внутри
`ScrollView` с hero-заголовком 200pt (градиент по времени суток + подпись-волна + иконка
времени суток справа-сверху + текстовый стек снизу-слева: дата `"EE · d MMM"` uppercase 11pt →
приветствие в `displaySerif(22)` → подпись-контекст 12pt), `.refreshable`,
`.navigationBarHidden(true)` (hero заменяет навбар), FAB'ы снизу-справа.

Содержание — из Mental, по `/today`:
- Свитч по `status`: `"active"` | `"selfcheck_due"` (week N — пора самопроверка) | `"completed"`.
- В `"active"`: `session` = `"morning"` (открыть день) либо `"evening"` (закрыть день);
  `done_today` — гейт, что сегодня уже закрывали день.
- Утро: `intent_questions` (спец для недели 6) → фокус дня + задание с подзадачами → аудио.
- Вечер: статус задания (`DONE`/`PARTIAL`/`NOT_DONE`) → квиз (варианты текстом) →
  3 вопроса рефлексии (свободный текст, с голосовым вводом).
- Карточка задания — по образцу `PlanItemCard` (раскрывающаяся карточка с цветной полосой
  3pt слева, `LabelTag` типа, заголовок, тело, chevron; spring-анимация). Это самый
  копируемый компонент Rhythmos.
- FAB'ы: основной 56×56 круг terracotta с `sparkles` — «Спросить ИИ»; вторичный 48×48
  инвертированный с обводкой и `pencil` — заметка в дневник.
- Пустые/загрузочные/завершённые состояния — по образцу Rhythmos (`PageCard` с иконкой 36–40pt,
  заголовком `titleS`, подписью по центру и `AccentButton`).

**ВАЖНО про маркеры:** 5 утренних + 5 вечерних маркеров состояния спрашиваются **раз в неделю**,
блоком непосредственно перед вопросами недельной самопроверки — НЕ каждый день. Это изменено
коммитом `9990668` (2 сентября 2026): раньше их спрашивали все 42 дня, это утомляло и не давало
новой информации. Деление morning/evening осталось **контентным** (два разных набора вопросов:
состояние на входе в день / как день сложился), а не привязкой ко времени суток.

### Вкладка 2 — «История»

По образцу `HistoryView` Rhythmos (643 строки): `MonthCalendarStrip` (месячная сетка 7×N,
недели с понедельника, кружок 28×28 на день, залитый terracotta для выбранного) как
навигатор/фильтр, под ним лента карточек дня, каждая — `NavigationLink` в детальный вид.
Два разных пустых состояния: «истории ещё нет» (иллюстрация + CTA, прыгающий на вкладку
«Сегодня» через прокинутое замыкание) и «в этот день записей нет» (тихая карточка).

Данные — `POST /api/v1/journal/list` `{provider, provider_user_id | user_id, module_code?}` →
`{entries:[{id, source_type, module_code, module_name, week, day, text, created_at}]}`,
отсортировано `created_at DESC`. `source_type ∈ task | reflection | final_product | note`.
У заметок и финального продукта `week`/`day` = `null`. `created_at` — наивный ISO без таймзоны.

### Вкладка 3 — «Пройденный путь» (новая, аналитика)

Этой вкладки в Rhythmos нет — она собирается из существующих эндпоинтов Mental:
- `GET /api/v1/enrollments/{eid}/status` → `{module, name, status, week, day, mode,
  total_weeks, total_days, days_completed, days_total, started_at, weeks:[{week, zone}]}`.
  Зоны недель (`GREEN`/`YELLOW`/`RED`) — визуальная шкала пройденного.
  Учти: `total_weeks`=6, `total_days`=7, `days_total`=42 **захардкожены** в бэкенде и не
  выводятся из контента.
- `POST /api/v1/enrollments/{eid}/week-insight` → `{enabled, text}` — ИИ-разбор последней
  пройденной недели.
- `POST /api/v1/enrollments/{eid}/insight` → `{enabled, text}` — итог программы.
- `POST /api/v1/final-products/list` → собранные «финальные продукты» (личные итоги программ).
- `POST /api/v1/users/enrollments` → все программы пользователя (так iOS и узнаёт свои `eid`).

В Rhythmos эндпоинты инсайтов существуют, но **UI для них не сделан** (`getWeeklyInsight`,
`getProgramInsight` есть в API-клиенте, экрана нет) — в Ridge это как раз третья вкладка.

### Онбординг — детальнее, чем в Rhythmos

Механика шагов берётся из `OnboardingView` Rhythmos (565 строк): плоский `@State step`,
`ProgressDashes` сверху, `choiceCard(icon:text:subtitle:isSelected:)` с `ChoiceGlyph`
(круг 42pt, заливка terracotta@0.13 при выборе) и `SelectionMark` (круг 26pt с белой галочкой),
`Haptics.selection()`, липкая нижняя панель с `GhostButton ‹ Назад` + `AccentButton Дальше →`,
и **escape-hatch «Пропустить →»**, ведущий на выбор программы вручную.

Содержание — из Mental:
1. **Шаг 0 — язык.** Заголовок двуязычный («Язык / Language»), чтобы читался до выбора.
   Активен только `🇷🇺 Русский`. Español / Deutsch / Português / English — неактивны, помечены
   «скоро». (Внимание: в бэкенде `SUPPORTED_LANGUAGES = ["ru","en","uk","es","de"]` —
   **португальского нет**, при добавлении нужно дописать `pt` в `backend/app/services/i18n.py`.)
2. **Вступление** — `GET /api/v1/intake` отдаёт `client_intro`: объяснение, что это 30 коротких
   вопросов, здесь нет правильных ответов, ориентир — последние 2–4 недели, и что
   **результат не является диагнозом**. Текст обязателен, он снимает тревогу и юридически важен.
3. **Интейк — 30 вопросов.** `GET /api/v1/intake?lang=ru` →
   `{version, client_intro, answer_scale, start_button, questions:[{n, direction, text}]}`.
   Шкала: 0 «совсем не про меня» · 1 «редко бывает» · 2 «иногда бывает» · 3 «часто про меня» ·
   4 «почти всегда про меня». Иконка вопроса — SF Symbol по его `direction`.
   Отправка: `POST /api/v1/intake/submit` `{provider, provider_user_id, answers:{"1":0..4,…"30":…}}`
   (ключи — СТРОКИ). Ответ — ведущее направление + 2 доп. фокуса + рекомендованная программа.
   ВАЖНО: пропущенные вопросы молча считаются нулями, а значение вне 0..4 даёт HTTP 500 —
   валидируй на клиенте.
4. **Результат** — рекомендация программы с правом выбора за пользователем (право выбора
   нормативное, не подменяй автопереходом).
5. **Напоминания** — `POST /api/v1/users/settings/update` `{slot, hour, minute}`, по одному
   слоту за вызов; слоты `morning`/`afternoon`/`evening`, дефолты 10:00/14:00/20:00,
   таймзона по умолчанию `Europe/Riga`.

Замечание: сейчас напоминания шлёт только Telegram-бот (`due_reminders` фильтрует
`provider == "telegram"`). Для iOS нужны **push** — их в бэкенде нет вообще, это отдельная
задача (APNs + хранение device token). На первом этапе можно локальные уведомления iOS.

## 5. Контракт API Mental — что важно знать клиенту

Полный список — 36 эндпоинтов в `~/dev/mental/backend/app/main.py` (449 строк). Ключевое:

**Язык передаётся двумя разными способами.** Три каталожных эндпоинта (`/modules`,
`/modules/{code}/weeks/{n}`, `/intake`) и оба аудио-эндпоинта берут язык из query `?lang=`.
**Все остальные** игнорируют `lang` и берут его из `User.preferred_language`. Значит iOS должен
и передавать `?lang=` для каталога, и сохранять язык на сервере через `/users/resolve`
(поле `language`) или `/users/settings/update`.

**Три формы ответа `/today`** — переключайся по `status` до декодирования:
`{"status":"completed"}` (2 поля) · `{"status":"selfcheck_due","week":n}` (2 поля) ·
полный активный payload (см. §3.2).

**День:** `POST .../open-day` (тело игнорируется) → `{session:"evening", week, day}`;
`POST .../close-day` `{task_status, task_answer, quiz_answer, reflection[]}` → `{status, week, day}`
— **это и есть продвижение дня**; `POST .../complete-day` — оба захода за раз (не заблокирован
для обычного режима). `close-day`/`complete-day` **не идемпотентны**: два вызова = два дня вперёд.
Защищай от двойного тапа.

**Самопроверка (день 7):** `GET .../selfcheck-questions` → `{week, questions:[{q, question,
options:[str]}], morning_markers:[{idx, question, options}], evening_markers:[...]}`.
Веса/критичность вырезаны намеренно (§16). `POST .../selfcheck` `{answers:{"1":idx,…"10":idx},
morning:{...}, evening:{...}}` — значения это **индексы вариантов (0-based)**, не тексты.
Работает только при `status == "selfcheck_due"`, иначе HTTP 500. Ответ — зона + рекомендация +
блоки по критичным ответам, баллы скрыты.

**Количество вариантов ответа:** 90 вопросов с 5 вариантами, 9 с 6, 3 с 7 — верстай списком,
не сегментами.

**Аудио:** `GET /api/v1/audio/{code}/resolve?lang=ru` → `{code, title, language,
requested_language, fallback, storage_key, mime, url, cached}`. Коды вида
`AUDIO_REAL_W1_A1` (`AUDIO_{МОДУЛЬ}_W{неделя}_{слот}`, слот `A1|A2|A3|FINAL`, 24 на программу).
`url` = `null`, пока не настроен `audio_public_base_url` — тогда берётся
`GET /api/v1/audio/{code}/file?lang=ru`. Соответствие дня и слота:
дни 1–2 → A1, 3–4 → A2, 5–6 → A3, 7 → FINAL.
**Внимание:** все 48 файлов в `content/audio/` сейчас — одна и та же заглушка (одинаковый md5),
реальная озвучка ещё пишется.

**Ошибки:** тела запросов объявлены как `payload: dict = Body(...)` — Pydantic-моделей нет,
валидации полей нет, `/openapi.json` не содержит схем запросов (клиент из спеки не сгенерировать).
Обработчиков исключений нет: `ValueError` в сервисах становится **HTTP 500**, а не 422.
Клиент должен трактовать 500 на `open-day`/`close-day`/`selfcheck` как «неверное состояние».
Осмысленных 422 всего четыре, 403 один (тест-режим).

**Свободные JSON-поля** — декодируй мягко: `quiz` (`{kind, question, options, correct,
saves_free_text}`, где `correct` и `saves_free_text` нигде не используются), `passport`
(словарь длинных строк: `name, intro, for_whom, extra_support, what_happens, why,
what_user_gets, main_result, important`), `task.subtasks`, `reflection`, `intent_questions`,
`key_themes` — массивы строк, возможно пустые. `sections` финального продукта — массив
многострочных строк, где **первая строка это заголовок**, остальное подсказка (разделяй по
первому `\n`).

## 6. Консистентность с ботом — обязательна

Приложение и Telegram-бот должны говорить одним голосом и одними терминами. Источник —
`~/dev/mental/bot/texts.py` (266 строк) и `keyboards.py`.

**Терминология (нормативные запреты, §16):**
- Слово **«диагностика» в UI запрещено** — только «самопроверка».
- Не «модуль», а **«маршрут»** или **«программа»** (в боте уже так).
- «Мы **не ставим диагнозов** и не заменяем работу с психологом» — эта оговорка есть на
  первом экране бота, должна быть и в приложении.

**Тон:** спокойный, без давления, обращение на «вы». Из бота: «спокойные 6-недельные маршруты
работы с собой», «шаг за шагом, в вашем темпе», «мягко и постепенно», «один день за раз»,
«маршрут идёт в вашем темпе». Эмодзи используются умеренно и осмысленно: 🌅 утро, 🌇 вечер,
🌙 завершение, 🧭 подбор маршрута, 🎯 фокус, 📝 задание, ✍️ рефлексия, 🎧 аудио,
🟢🟡🔴 зоны, 🌿 общий знак продукта.

Прочитай `bot/texts.py` целиком перед написанием текстов приложения и переиспользуй формулировки
там, где они уже удачны — расхождение в словах между каналами читается как два разных продукта.

## 8. Чего делать НЕ надо

- Не переноси предметную логику Rhythmos: ритуалы, чек-ины энергии/напряжения (шкалы 1..5
  с «атмосферными» градиентами), theme engine, программы 7/14 дней, `PracticesLibraryView`.
  Из `APIModels.swift` (1232 строки) переносится примерно 200 строк инфраструктуры
  (`AuthResponse`, `APIError`, `AnyCodable`, форма профиля), остальное — домен Rhythmos, удалить.
- Не трогай внутренние имена Mental: контейнеры `mental-backend`/`mental-db`/`mental-bot`,
  каталог `~/dev/mental`, коды `AUDIO_REAL_*`, `DATABASE_URL`. Они не видны пользователю,
  а переименование на живом сервере — риск без выгоды. Ridge — это имя **продукта**, а не репозитория.
- Не выдумывай эндпоинты. Если чего-то не хватает (push-токены, `day_steps`, авторизация) —
  добавь в бэкенд явно и скажи об этом, а не имитируй на клиенте.
- Не пиши «диагностика», «модуль» в пользовательских текстах.
- Не хардкоди строки в вью и не прибивай форматтеры к `ru_RU`.

## 9. Открытые вопросы — спроси владельца, если упрёшься

- **Push-уведомления**: APNs в бэкенде Mental нет вообще, напоминания только через Telegram.
  На первом этапе — локальные уведомления iOS или сразу APNs?
- **Один активный маршрут**: бэкенд позволяет пользователю держать несколько enrollment'ов

  `date.today()` серверного процесса — то есть «день» считается по времени сервера,
  а не пользователя. Исправлять сейчас или позже?
